# 01. 브랜치 전략

> 브랜치 = **작업 공간을 복사해서 따로 작업하는 것**입니다.
> 여러 명이 같은 파일을 동시에 고쳐도 서로 방해하지 않게 해 줍니다.

---

## 우리 팀 브랜치 구조

```
main                    ← 🔒 발표·제출용. 항상 동작하는 완성 코드만.
 └── develop            ← 🧩 개발 기준 브랜치. 모든 기능이 여기로 모입니다.
      ├── feat/login            (A팀원 작업 중)
      ├── feat/event-search     (B팀원 작업 중)
      └── fix/map-marker        (C팀원 버그 수정 중)
```

| 브랜치 | 역할 | 직접 push |
|---|---|---|
| `main` | 발표·제출 시점의 **안정 버전**. 깨지면 안 됨 | ❌ 금지 |
| `develop` | 개발 중인 코드가 모이는 **기준 브랜치** | ⚠️ PR 권장 |
| `feat/*` | 새 기능 개발 | ⭕ 자유 |
| `fix/*` | 버그 수정 | ⭕ 자유 |
| `docs/*` | 문서 작업 | ⭕ 자유 |
| `chore/*` | 설정·환경 작업 (빌드 설정 등) | ⭕ 자유 |

---

## 브랜치 이름 규칙

```
<종류>/<작업내용-영문소문자-하이픈>
```

### ✅ 좋은 예

```
feat/login-api
feat/event-search-filter
feat/ai-plan-generate
fix/map-marker-overlap
docs/readme-update
chore/gitignore-setup
```

### ❌ 나쁜 예

| 이름 | 문제 |
|---|---|
| `test` | 무슨 작업인지 알 수 없음 |
| `내작업` | 한글은 환경에 따라 깨질 수 있음 |
| `feat/로그인` | 위와 같음 |
| `junseo` | 사람 이름만으로는 내용을 모름 |
| `feat/Login_API` | 대문자·언더바 대신 소문자·하이픈 사용 |

## 작업 흐름 (한 사이클)

```bash
# 1. develop 최신화
git checkout develop
git pull origin develop

# 2. 내 브랜치 생성
git checkout -b feat/login-api

# 3. 작업 → 커밋 (여러 번 해도 됨)
git add .
git commit -m "feat: 로그인 API 구현"

# 4. 올리기
git push origin feat/login-api

# 5. GitHub에서 PR 생성 (base: develop ← compare: feat/login-api)

# 6. 팀원 확인 후 Merge

# 7. 병합된 브랜치 정리
git checkout develop
git pull origin develop
git branch -d feat/login-api          # 내 컴퓨터에서 삭제
```

## 담당 영역별 브랜치 예시

요구사항 정의서의 모듈 구분을 참고한 예시입니다.

| 담당 모듈 | 브랜치 예시 |
|---|---|
| 회원가입·로그인 (Auth) | `feat/auth-signup`, `feat/auth-login` |
| 행사 검색 (Search) | `feat/search-condition`, `feat/search-keyword` |
| 외부 데이터 연동 (Data) | `feat/data-seoul-event-api`, `feat/data-tour-api` |
| 일정 생성·편집 (Plan) | `feat/plan-generate`, `feat/plan-edit-order` |
| 지도 (Map) | `feat/map-marker`, `feat/map-route-line` |
| 즐겨찾기 (Favorite) | `feat/favorite-toggle` |
| 마이페이지 (My) | `feat/my-plan-list` |
| 화면 UI | `feat/ui-main-page`, `feat/ui-login-page` |

## 규칙 정리

1. **`main`에서 직접 작업하지 않습니다.** 항상 `develop`에서 브랜치를 땁니다.
2. **브랜치 하나 = 작업 하나.** 로그인 브랜치에서 지도 작업까지 하지 않습니다.
3. **작업 시작 전 `git pull origin develop`** — 충돌을 크게 줄여줍니다.
4. **브랜치는 오래 두지 않습니다.** 길어질수록 충돌이 커집니다. 기능 단위로 잘게 나눠 빨리 합치세요.
5. **PR은 develop으로** 보냅니다. `main`으로 보내는 건 발표·제출 직전 한 번뿐입니다.

---

## main에 반영하는 시점

발표·제출 등 **완성 시점**에만 `develop → main` PR을 만듭니다.

```
develop  ──(PR)──▶  main
```

이때는 반드시 팀 전체가 동작을 확인한 뒤 합칩니다.
